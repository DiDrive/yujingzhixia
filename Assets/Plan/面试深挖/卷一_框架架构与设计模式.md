# 卷一：框架、架构与设计模式

## 1. 这个项目究竟有没有“框架”？

### 面试官真正考什么

不是让你报出 MVC、ECS 或某个第三方框架名称，而是判断你是否知道对象由谁创建、依赖由谁连接、数据归谁拥有、模块怎样通信、切场景后谁继续存在。能回答这些，才说明项目有架构；只有文件夹分类不算框架。

### 准确定义

本项目不是严格 MVC/MVVM，也没有使用 VContainer、Zenject 或完整 ECS。更准确的描述是：以 MonoBehaviour 承载 Unity 生命周期，以 Service 管理玩法数据和用例，以 Bootstrap 装配场景对象，以接口、局部事件和 EventBus 处理不同耦合度通信，以 JSON、ScriptableObject、Prefab 和 Inspector 共同驱动配置的轻量分层框架。

### 真实运行结构

`PersistentGameServices` 决定跨场景服务的所有权；`SceneFlowController` 编排场景切换；`GameBootstrap` 和 `ShelterSceneController` 分别装配局内与基地；`GridInventoryService`、`SurvivalSystem`、`LootTableDatabase` 等提供玩法能力；Player、Zombie、UI 和地图对象属于具体场景。数据层向上提供能力，表现层不能反向成为真实数据源。

### 为什么这样做

个人 Demo 需要任意场景直接 Play，所以两个场景预摆核心；同时又必须保证撤离后库存不丢，于是第一套核心常驻、后加载副本销毁。玩家和 UI 不常驻，因为基地与局内的出生点、相机、Collider 和界面不同。这个方案优先解决开发便利性和生命周期正确性，而不是追求抽象数量。

### 当前缺陷

装配仍不纯粹：多个业务组件会自行 `FindObjectOfType`；`GameBootstrap` 职责偏多；服务多为 MonoBehaviour，纯领域逻辑不完全脱离 Unity；静态仓库和事件总线增加测试隔离难度。因此只能叫“轻量项目框架”，不能包装成通用商业框架。

### 连续追问

- 框架和架构有什么区别？架构是高层结构和约束，框架通常还提供可复用控制流与扩展点；本项目更偏架构骨架。
- 为什么不直接使用现成框架？当前规模下引入成本可能高于收益，但应保留可迁移边界。
- 怎样证明边界有效？替换 UI 时领域规则无需修改；从基地切局内时同一库存仍存在；世界容器可复用同一背包服务。

## 2. 分层的依据是什么，为什么不是按功能随便分目录？

### 核心原则

分层依据是变化原因和依赖方向。UI 因视觉和交互变化；领域规则因玩法规则变化；配置因数值变化；基础设施因存储或资源技术变化。把不同变化原因放在同一类中，就会出现修改按钮布局却碰坏库存，或更换 JSON 库却修改战斗代码。

### 当前依赖链

以背包拖放为例：`GridInventoryUnityUI` 接收 PointerEvent，计算目标容器和格子；调用 `GridInventoryService.TryMove`；Service 查询 `GridItemDefinition`、目标容器和 `GridOccupancyMap`；`GridPlacementSolver` 计算 footprint 并验证；成功后模型提交，UI 再按模型刷新。核心规则不知道 RectTransform、鼠标和 Canvas。

### 为什么 Service 仍然不是纯 Domain

`GridInventoryService` 继承 MonoBehaviour、使用 SerializeField、Resources 和 Unity 类型，所以它同时承担 Application Service 与部分 Infrastructure。原型阶段这样减少装配成本；正式拆分时应把 Occupancy、Placement、Transaction 和实体集合放入普通 C# 程序集，MonoBehaviour 只负责序列化配置和转发生命周期。

### 违反依赖方向的后果

如果 Service 直接调用某个按钮变灰，换 UI Toolkit 就必须修改领域服务；如果 UI 直接改 instance.originRow，占用图和成员表不会同步；如果存档直接序列化 GameObject，场景重建后引用失效。依赖方向不是审美，而是保护状态一致性和可替换性。

### 连续追问

- Domain 能否引用 `Vector2Int`？技术上可以，但会让纯程序集依赖 UnityEngine；可以自定义 GridPosition 或接受这个有限依赖，取决于测试和复用目标。
- DTO 放哪层？边界层；存档 DTO 不应承载领域行为。
- UI 是否能缓存状态？可以缓存 ViewModel 和临时交互状态，但不能成为库存权威。

## 3. Composition Root 和依赖注入在项目里到底做到什么程度？

### 定义

Composition Root 是创建对象并连接依赖的集中位置。依赖注入是“依赖从外部传入”，并不等于必须使用 DI 容器。Inspector 字段、`Bind`、`Configure`、构造参数都可以是注入方式；对象自己全局查找依赖则是 Service Locator。

### 项目证据

`ShelterSceneController` 获取常驻的 Inventory、Survival 和 Shelter 服务，实例化场景玩家，再把服务、主背包 UI 和 Prompt UI 传给 `PlayerInteractor2D.Bind`。`GameBootstrap` 在局内做类似装配。编辑器 Builder 通过 `Configure` 写入场景引用。这些都是手动注入和 Composition Root 的雏形。

### 为什么还保留 Find

场景可独立 Play、旧 Prefab 可能缺引用、玩家运行时生成，因此 Find 作为兼容回退能提高原型鲁棒性。但它隐藏真实依赖，并且场景短暂有两个服务时可能找到错误实例。最佳演进不是“全项目禁止 Find”，而是只允许 Bootstrap 定位一次，随后显式注入；业务对象缺依赖应快速失败。

### 构造注入为什么难直接用于 MonoBehaviour

MonoBehaviour 由 Unity 创建，不能用普通 `new` 和自定义构造流程。可把纯逻辑放普通 C# 类，用构造注入；MonoBehaviour 用序列化字段或 Initialize。Initialize 后才能使用的对象要有状态保护，防止 Awake/OnEnable 先于注入执行。

### 是否应该上 DI 容器

当注册项、生命周期 Scope、替换实现和测试装配明显增加时，VContainer 等能减少手写装配。但容器也会隐藏调用链、增加启动学习成本。当前项目先收敛 Composition Root 和接口边界，比立即换框架更重要。

### 连续追问

- 属性注入有什么风险？对象可能在依赖未赋值时已可见，无法保证创建即有效。
- 为什么静态单例不是注入？调用者主动获取全局对象，依赖没有从外部提供。
- 如何测试 MonoBehaviour？把纯用例抽出，MonoBehaviour 只作为 Adapter；PlayMode 只测连接。

## 4. InventoryService 为什么既是 Facade 又是 Adapter？

### Facade 的意图

Facade 为复杂子系统提供更小、更稳定的入口。工作台和夜袭奖励只想知道能否 `AddItem`、`ConsumeItem`、`CountItem`，不应理解二维格、旋转、实例 ID 和容器优先级。`InventoryService` 正是这种门面。

### Adapter 的意图

项目早期模块使用 `itemId + quantity` 的旧库存语义，新网格背包使用实例、容器和坐标。`InventoryService` 把旧接口转发到 `GridInventoryService`，并删除第二份 Stacks，因此也在适配两种接口模型。

### 两个模式为何能重叠

模式描述的是设计意图，不是互斥标签。同一个类既可简化复杂接口，也可让旧客户端适配新后端。面试时要讲意图和调用关系，而不是说“用了两个高级模式”。

### 当前接口为什么不够成熟

bool 无法区分 NoSpace、InvalidItem、LockedCell 或 TagRejected；Count/Consume 只统计 Player Owner，调用者若不了解归属规则可能误用；工作台多次 Consume 后产物 Add 失败会丢材料。未来应提供 `InventoryResult` 和原子 `TryExchange` 用例，并把读写接口拆成 `IInventoryReader`、`IInventoryWriter`。

### 连续追问

- Facade 会不会变成 God Object？会，如果不断把所有业务塞入门面；门面应转发用例，不拥有无关状态。
- Adapter 和 Decorator 区别？Adapter 改接口以兼容，Decorator 保持接口并叠加职责。
- 为什么不让工作台直接依赖 GridInventoryService？会扩大上层知识面并阻碍替换。

## 5. 敌人组件为什么属于 Strategy，而不是 State？

### Strategy 的判定

Strategy 把可互换算法封装起来，由 Context 委托执行。`ZombieController2D` 是 Context；`EnemyMovement2D.GetVelocity` 和 `EnemyAttack2D.TickAttack` 定义行为接口；追击移动与近战攻击是具体策略。不同敌人可组合不同移动和攻击，而无需在控制器中按 enemyType 写分支。

### State 的判定

State 关注同一对象随内部状态变化而切换行为，例如 Idle、Chase、Attack、Hit、Dead。当前 Zombie 控制器内部确实存在状态式控制，但没有把每个状态封装成对象，所以它只是 enum/条件驱动 FSM，不是完整 GoF State 类模式。

### 为什么区别重要

“近战攻击”是可替换能力，可以和不同移动组合；“死亡”是对象生命周期状态，死亡后必须禁用移动、攻击和碰撞。把两者混为一种模式会导致组合爆炸，例如为 ChaseMelee、ChaseRanged、PatrolMelee 各写状态类。

### 当前策略的局限

策略仍继承 MonoBehaviour并直接访问 Transform/Animator，难以纯单测；Attack 策略还包含计时和动画 fallback。商业化可把决策算法放普通 C#，把动画、Rigidbody 作为 Port/Executor；或者保留组件策略，用 PlayMode 测试其协作。

### 连续追问

- Strategy 与 Template Method 区别？Strategy 用组合替换整个算法；Template Method 用继承固定流程骨架，只让子类覆盖步骤。当前抽象类没有一个固定骨架方法调用多个 Hook，因此不应说用了 Template Method。
- ScriptableObject 能否做策略？可以，适合无场景状态的共享算法，但不能把每个敌人的可变冷却直接写在共享资产上。

## 6. EventBus 是观察者、消息总线还是中介者？

### 准确定性

`EventBus` 用事件类型映射 Delegate，发布者 `Publish<T>`，订阅者 `Subscribe<T>`，属于 Observer 思想和 Event Aggregator/轻量消息总线。它不是严格 Mediator，因为没有一个对象显式协调参与者业务流程；也不是异步消息队列，因为 Publish 在当前线程同步调用。

### 为什么项目同时使用 C# event

僵尸与尸体控制器是局部、强关系，`ZombieController2D.Died` 能直接表达来源并容易跟踪；GamePhaseChanged 或 ExtractionCompleted 可能被多个跨系统对象关心，用 EventBus 避免发布者持有所有订阅者。选择取决于关系范围，不是 EventBus 比 event 更高级。

### 同步 Publish 的语义

订阅者在 Publish 返回前执行。它们耗时会阻塞发布者；异常若不隔离会终止后续订阅；订阅顺序依赖 Delegate 组合顺序，但业务不应依赖这个隐含顺序。需要强顺序和失败回滚的流程应显式调用，而不是广播。

### 静态生命周期风险

Handlers 静态字典可能跨场景甚至在关闭 Domain Reload 后保留；订阅者销毁但未 Unsubscribe 会留下引用或产生 MissingReference；测试之间也会污染。应在 SubsystemRegistration 清空、订阅返回 IDisposable Token、OnEnable/OnDisable 成对管理，并提供诊断日志。

### 高频事件问题

`SurvivalTickEvent` 每帧发布不理想。HUD 可按变化阈值或低频刷新，事件应表达“属性变化”而非“每帧到了”。高频全局广播使调用链不可见，也可能放大 UI 文本分配。

### 连续追问

- 事件能返回值吗？技术上 Delegate 可以，但一对多结果语义不清；需要结果用直接调用。
- 弱引用事件是否万能？能降低引用泄漏，却增加复杂度并掩盖错误的生命周期管理。
- 怎样测试？注入 `IEventBus` 或 RecordingBus，断言事件和负载；每个测试后清理。

## 7. GameStateMachine 是否真的算状态机？

### 为什么算

它有有限状态集合 `GamePhase`、当前状态、改变状态的动作和变化事件，因此是轻量有限状态机。状态少、行为主要由其他系统根据 Current 判断时，enum FSM 足够。

### 为什么不是完整 State Pattern

没有 `IGameState.Enter/Tick/Exit` 对象，也没有显式转移表。`StartRun`、`EnterRaid` 等方法只是把 next 传给 ChangeState；如果从 Result 错误调用 EnterRaid，内部没有阻止。状态行为分散在 Survival、NightAssault 和场景流程中。

### 如何升级

第一步加 `CanTransition(from,to)` 和 `TryChangeState` 错误结果，建立合法转移图。第二步当 Enter/Exit 行为变多，再引入状态对象。切换顺序应定义为验证→Exit旧状态→更新 current→Enter新状态→发布 Changed；Enter 失败的回滚策略也要明确。

### 为什么不一开始就状态对象化

五个简单状态若各建类、工厂、上下文，会增加文件和间接层，却未解决真实复杂度。模式应在行为和转移复杂到值得抽象时使用。能说明“不用模式的理由”也是设计能力。

### 连续追问

- 状态与阶段区别？阶段是业务流程状态；角色状态通常更高频、更复杂，可用不同状态机。
- 状态切换可以在事件订阅者中再次切换吗？会重入，应加 transition guard 或队列。
- 如何存档？保存稳定 enum/字符串 ID；加载时恢复状态还要明确是否重放 Enter。

## 8. WorldInteractableRegistry 为什么是 Registry 模式，它解决什么而不是解决一切？

### 机制

交互物 OnEnable 时登记 Behaviour、接口和自身/子物体 Collider；OnDisable 时移除。Interactor 只遍历 Registry Entries，再做楼层、CanInteract、Layer、ClosestPoint、距离和 Linecast 精确过滤。

### 相比场景查找

`FindObjectsOfType` 会遍历 Unity 对象并生成结果，频繁使用昂贵；Registry 把发现成本分摊到对象生命周期。相比 OverlapCircleAll，它不会被大量 Tilemap Collider 淹没，也无需每次从 Collider 反查接口。

### 它不是空间索引

Registry 仍是 List，扫描复杂度 O(N)。几百个激活交互物且每秒十余次扫描可能足够；成千上万时应按网格、四叉树或区域分桶。不能只因“有注册表”就声称高性能。

### 正确性风险

静态 List 也有 Domain Reload 残留；对象异常销毁可能未注销；缓存 Collider 后运行时新增 Collider 不会自动更新；同一 Behaviour 重复注册需去重。当前 Register 先 Unregister，并在注销时清 null，但还应提供静态 Reset 和开发期一致性检查。

### 连续追问

- 为什么不用 NonAlloc 物理查询？可以，需专用 Layer、固定缓冲区和溢出策略；最终要基准测试。
- ClosestPoint 为什么重要？大 Collider 按 Transform 中心算距离会误判。
- LOS 为什么单独交互点？墙内中心和穿墙 Collider 会让射线终点不符合实际操作侧。

## 9. 搜索状态为什么只是 Memento 思想，而不是完整 Memento 模式？

### Memento 的核心

在不让外部随意破坏对象内部约束的情况下，捕获某时刻状态并在以后恢复。项目导出容器是否生成、是否搜索、物品布局、数量和揭示状态，Store 保存 Clone，重进场景再恢复，符合“状态快照”思想。

### 为什么只说思想

没有通用 Originator/Caretaker 角色、历史栈、撤销/重做和多版本快照；Store 是专门的会话级静态仓库。因此准确表达是 Memento/Snapshot 思想，而不是完整通用 Memento 框架。

### Clone 的意义

如果 Store 直接返回内部 List，容器拿到引用后修改揭示状态，就绕过 Save；多个容器也可能共享可变对象。写入和读取都 Clone，保证仓库拥有自己的快照。深拷贝必须覆盖嵌套 List，否则只是浅拷贝。

### 稳定 ID 的必要性

Transform 位置或 GameObject 名称变化会让自动 ID 漂移，所以正式地图应显式 persistentId 并做 Editor 唯一性校验。运行时尸体用 runId+敌人唯一 ID。没有稳定身份，再完整的字段也找不到要恢复哪个对象。

### 连续追问

- 快照和事件溯源区别？快照保存当前结果；事件溯源保存导致结果的事件序列。
- 为什么不用 PlayerPrefs？复杂结构、版本迁移、原子写入和多存档槽不适合。
- 快照何时保存？关闭、卸载、关键变化；定时保存是容错但应避免无变化复制。

## 10. Definition/Instance 分离是不是 Flyweight？

### 数据语义

`GridItemDefinition` 是同类物品共享的内在状态：尺寸、名称、标签、堆叠上限和效果。`GridItemInstance` 是外在、可变状态：唯一 ID、数量、容器、位置和旋转。156 个定义可被任意数量实例引用。

### 与 Flyweight 的关系

这与共享内在状态以减少重复的 Flyweight 思想一致，但项目没有通用 Flyweight Factory 或透明共享对象生命周期。因此表述为“Flyweight 式数据分离”更严谨。

### 为什么对存档也重要

存档只需保存 itemId 和实例变化字段，加载后从配置表恢复公共定义。如果把 Sprite、显示名和效果复制进每个实例，存档膨胀且配置更新后旧实例数据不一致。

### 配置变化的风险

加载旧存档时 itemId 可能不存在、尺寸变大导致原位置放不下、maxStack 变小。必须有 LostAndFound、重排或拆分迁移规则。Definition 共享减少重复，但把兼容责任集中到了配置版本迁移。

### 连续追问

- Definition 应用 struct 还是 class？当前 struct 在 Dictionary 取出时复制，修改必须写回；只读定义可用 immutable class/readonly struct，取决于大小和序列化。
- ScriptableObject 是否更好？需要 Unity 资源引用时好；大批表格数据的外部维护和 Diff 则 JSON 更方便。

## 11. 背包回滚为何属于 Transaction 思想？

### 事务不等于数据库

事务的核心是把多个状态修改视为一个原子操作，并保护不变量。批量 Add 可能先填充旧堆叠，再创建新实例，再把实例放入多个容器；最后一步失败却保留前面变化，就是半提交。

### 项目如何做

操作前记录被修改堆叠的旧数量，并收集本次新建实例 ID。任何新实例创建或放置失败，就恢复旧数量并移除新实例。跨容器移动保存旧容器、坐标和旋转，目标填充失败时恢复旧占用。

### 维护的不变量

总数量守恒；每个实例最多属于一个容器；实例坐标与占用图一致；成员列表与 containerId 一致；一个格子只有一个 occupant；失败操作对外不可见。面试时先说不变量，再说代码，深度远高于“我做了回滚”。

### 当前还不完整

AutoSort 直接修改正式状态，失败时没有整体快照；Workbench 先扣材料再 Add 产物，也不是原子交换。更完善方案是两阶段提交：先在临时模型完整规划和验证，全部成功后一次 Commit；或设计 InventoryTransaction 统一记录 Undo。

### 连续追问

- 为什么不用异常回滚？背包满是预期失败，不应用异常控制；仍需显式撤销状态。
- 多线程需要锁吗？当前 Unity 主线程执行；若后台/联网并发，需版本号、锁或服务器权威。
- UI 会看到中间状态吗？当前同一帧同步执行通常看不到，但事件若在每一步发布就会泄露；应提交后统一发 changeSet。

## 12. SOLID 如何用项目事实回答，而不是背定义？

### SRP

`GridPlacementSolver` 只负责几何放置，职责清晰；`GridInventoryUnityUI` 同时负责布局、拖拽、选择、菜单、搜索遮罩和调试生成，违反信号明显。拆分依据应是变化原因，不是每 300 行一个类。

### OCP

新增 `WorldLootItem`、`SearchableLootContainer`、`ShelterInteractionPoint` 都可实现 IWorldInteractable，不改 Interactor，体现对交互类型扩展开放。消耗效果却用字符串 switch；新增效果必须修改 Service，可改 Handler Registry 或效果策略。

### LSP

`EnemyAttack2D` 子类必须遵守 `WantsToAttack/TickAttack/IsAttacking` 的语义。如果某个子类在 TickAttack 销毁 Context 或忽略距离却未说明，就破坏替换。LSP 需要契约和测试，不是“用了继承就满足”。

### ISP

IWorldInteractable 当前字段较多但对现有对象都合理。若未来存在无 Transform 的远程交互、无需 LOS 的 UI 终端，继续加字段会迫使实现空成员，应拆成 `IInteractable` 加可选 `IRequiresLineOfSight/IHasFloor` 能力。

### DIP

Interactor 依赖 IWorldInteractable、命中依赖 IHitReceiver，是良好实例；NightAssault 依赖具体 InventoryService，存档还没有 Repository 接口，是改进空间。高层用例依赖抽象并不意味着所有类都建接口，只有存在替换边界或测试价值时才值得。

### 连续追问

- SOLID 会不会过度设计？会；接口和间接层有认知成本，应围绕真实变化点使用。
- 怎样衡量拆分成功？依赖减少、测试更容易、修改一种变化不触碰无关模块，而不是文件数量变多。
