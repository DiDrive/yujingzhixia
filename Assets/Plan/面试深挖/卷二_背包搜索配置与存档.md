# 卷二：网格背包、搜索、配置与存档

## 1. 二维占用矩阵为什么是核心，而不是 UI 格子数组？

背包规则关心的是离散空间：一个物品从左上角 `(row,column)` 开始，占据 `width×height` 的区域。UI 格子只是显示，可能缩放、换 Canvas 或完全不存在；若用 RectTransform 重叠作为规则，分辨率和布局会污染数据。

`GridOccupancyMap` 分别保存 `occupied`、`occupantInstanceIds` 和 `locked`。判断区域时先用起点和终点验证边界，再逐格检查锁定和占用。同容器移动允许忽略自身 instanceId，否则物品覆盖旧区域时会与自己冲突。保存 occupant ID 而非 bool，还能从点击格反查实例。

复杂度方面，单次区域验证约为 `O(w×h)`；First Fit 最坏扫描所有起点，约 `O(R×C×w×h)`。百级格子下比维护复杂空闲矩形树更可靠。若仓库扩大到数万格，可用位图行掩码、空闲矩形索引或空间分区，但必须先基准测试。

必须测试：负坐标、右下越界、1×1、旋转、锁格、部分覆盖、忽略自身、容器零尺寸。正确性不是“拖起来正常”，而是每次操作后验证实例、占用图和成员列表双向一致。

## 2. First Fit 为什么可用，又为什么不等于最优装箱？

First Fit 按固定顺序遍历旋转和格子，遇到第一个可放位置立即返回。优点是确定性、实现小、便于调试；同样输入能得到同样布局。缺点是局部贪心，早期小物品可能切碎空间，让后续大物品放不下。

二维装箱接近 NP-hard，商业背包也不一定追求数学最优，而更重视玩家可预测和执行速度。自动整理可以先合并堆叠，再按面积、最长边或类型排序后 First Fit Decreasing，提高结果，但仍不保证全局最优。

若面试官问“怎么提高成功率”，可以回答：尝试多种排序和旋转顺序，在临时 OccupancyMap 中分别求解，选浪费最少的结果；设置时间预算；规模小可回溯搜索并剪枝。无论如何都应先在临时状态完整求解，成功后提交，不能直接破坏正式库存。

## 3. AddItem 的原子性怎样逐步证明？

输入数量可能跨越多个堆叠。算法先找同 itemId、目标容器内未满实例，按容器优先级和现有数量合并；剩余数量按 maxStack 拆成新实例，再依次 First Fit。

危险点在于：合并旧堆叠已经修改状态，而新实例后来可能放不下。项目记录每个被修改实例的旧 stackCount，并记录所有新建 instanceId；任何失败就恢复旧数量、清理新实例及其占用。于是失败前后 `CountItem` 相同。

还要验证更强不变量：回滚后旧实例 ID 不变、旧位置不变、容器成员无残留、占用图无幽灵 occupant。测试应构造“第一个新堆叠能放、第二个放不下”的场景，否则测不到半提交问题。

更完整实现会让操作在 InventorySnapshot/Transaction 中进行，提交时生成一个 changeSet；UI 和事件只看到最终提交，避免中间状态泄漏。

## 4. 拆分、合并和精确消耗有哪些隐蔽边界？

拆分要求 `0 < splitCount < source.stackCount`，新堆叠不得超过上限。创建新实例后若源已有位置，需要为新实例找到合法位置；失败必须删除新实例并恢复源数量。合并要求 itemId 相同、目标未满，移动量取 `min(target剩余容量, source数量)`；源归零时同时清占用、成员表和实例字典。

“按 itemId 消耗”和“按 instanceId 消耗”语义不同。制作可以按 itemId 从最小堆叠开始扣；玩家点击使用必须扣当前选中的 instanceId，否则两个相同罐头中可能消耗错误的一组，破坏 UI 选择和搜索引用。

如果实例被任务、快捷栏或搜索队列引用，合并导致 ID 消失必须定义映射策略。当前原型引用范围有限；正式项目可保留目标 ID、发布 `InstanceMerged(source,target)`，让引用方迁移。

## 5. 搜索交互为何要同时验证距离、楼层、视线和持续有效性？

任何单一条件都不够。Transform 中心距离会让长柜子边缘不可交互，所以用 Collider.ClosestPoint；只看距离会隔墙搜索，所以 Linecast；全楼层墙 Mask 会让二楼墙投影挡住一楼，所以只动态加入玩家当前 Wall_Fx；只在开始时检查会让玩家按住后走到墙后仍完成，所以持有期间持续复核。

贴墙容器的 Transform 可能位于墙内，ClosestPoint 也可能在错误一侧，因此提供显式 `interactionLineOfSightPoint` 表达实际操作面。扫描期间按住后锁定目标，避免相邻容器距离微变导致进度反复重置。

性能上使用 Registry 候选和扫描间隔，再对少数 Collider 做精确检查。正确性测试包括：同楼层/异楼层、隔墙、贴墙两侧、离开范围、持有时换楼、多个目标等距和目标禁用。

## 6. 逐件揭示为何是一个状态机，而不是一根进度条？

容器先有“未搜索/已搜索”，物品又有“排队/正在揭示/已揭示”。首次打开按格子行列建立确定队列；当前索引对应唯一实例，elapsed 根据品质换算时长；完成后进入 revealed 集合并推进到下一个未揭示项。

未揭示物品禁止拖拽、旋转、拆分和丢弃，是为了防止队列引用和玩家认知被破坏。玩家后来放入容器的物品不属于未知掉落，默认已揭示。若当前实例被外部移除，状态机要跳过而不是永久卡住。

存档不能只保存 currentIndex，因为实例恢复后 ID 可能变化。应保存稳定的物品状态或恢复时建立旧 ID→新 ID 映射，再重建 revealed/queue。当前实现已有恢复实例 ID 的入口，这是值得讲的细节。

## 7. JSON 配置从“能读”到“可生产”还差什么？

`JsonUtility` 能读取固定 DTO，但不会自动保证业务正确。生产级校验必须检查重复/空 itemId、非法尺寸、maxStack、Profile 引用、效果类型、Resources 图标路径、掉落表未知物品、数量范围、全零权重和重复 tableId。

校验应复用同一核心，在 Editor 菜单、构建前处理和 CI 中运行；严重错误阻止 Build，警告给出资产路径和修复建议。配置根带 schemaVersion 和 contentHash，存档记录版本。字符串效果类型容易拼错，可用 enum DTO 或 Handler Registry；若仍用字符串，要集中 Normalize 和白名单校验。

JSON 与 ScriptableObject 的选择不是信仰：大量表格、外部工具和版本 Diff 适合 JSON；Prefab、Sprite、Animator 等 Unity 引用适合 SO。项目的混合方案合理，但 Resources 路径仍是字符串弱引用，内容扩大后可迁到 Addressables Key 或生成强类型索引。

## 8. 正式存档为什么不能只是 JsonUtility.ToJson 后 File.WriteAllText？

先定义保存边界：只存稳定 ID 和纯数据，不存 GameObject、Sprite 或运行时引用。根对象包含 schemaVersion、saveId、runId、时间、玩家/仓库容器、生存属性、发现状态和本局容器快照。

写入必须抗中断：序列化到 `slot.tmp`，写完 Flush 并校验，再原子替换正式文件，同时保留 `.bak`。加载先校验格式和版本，失败尝试备份。版本迁移按 V1→V2→V3 的相邻步骤执行，并保留历史 golden saves 自动测试。

配置变化也要迁移：删除 itemId 放入 LostAndFound；容器缩小先临时重排，溢出物品进入邮件/溢出区；maxStack 变小要拆堆。撤离流程应把“判定成功、结算库存、写盘成功、加载基地”分开，写盘失败不能悄悄进入基地并声称已保存。
